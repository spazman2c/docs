title: "Errors, credits and pagination"
description: "Handle hosted API errors, empty coverage and uncertain delivery without automatic retries."
---

HTTP responses use typed pages or structured problem objects. Read `data`, `missing[]` and `meta` together. A successful HTTP status does not mean every requested source is covered.

## What to do with a response

| Status | Meaning and next step |
| --- | --- |
| 200 / 201 | Inspect the returned page, missing coverage and current state. An empty data page can be a valid result. |
| 304 | No response body. Reuse only the cached representation for the same query and ETag; do not parse a JSON body. |
| 400 / 422 | Fix the named `invalid_params` or narrow the request. Retrying unchanged input will not help. |
| 401 | Check the header key or session. It may be missing, invalid, expired or revoked. |
| 403 | The current role, feature, namespace or source-purpose access does not permit this request. Signup is not a grant. |
| 402 | No data allocation or insufficient included credits. Inspect free usage/entitlements; overage is disabled. |
| 409 | Query/cursor or mutation state changed. Explicitly restart a read traversal, or reconcile the existing mutation request ID. |
| 410 | A beta invitation expired. Ask support rather than changing or reusing an invitation. |
| 429 | A separate abuse/rate window applied. Read `Retry-After` and decide when to try again. |
| 503 / 504 | A required data/control dependency is unavailable or a deadline expired. Keep the request ID; do not substitute cached active odds. |

A problem includes `code`, `request_id`, `detail`, `invalid_params` and `missing`. Report the operation and request ID to support. Do not send keys, bearer tokens or raw private customer data.

## Credits and uncertain delivery

Completed successful canonical data pages cost one included credit, including empty and insufficient results. Native fixture pages with no fixtures and native odds pages with no eligible records are free; nonempty eligible native pages cost one credit. Account/control/coverage requests, errors, 304 responses and WebSocket messages are free. This does not allocate any credits to a new account.

A timeout or disconnected client can have an **unknown delivery outcome**. The server may have completed a response even if your program did not receive it. Never assume an interrupted call was free or retry it silently. Inspect [Usage](https://oddswire.io/app/usage) and request metadata before a deliberate retry. The quick starts make no automatic retries.

`X-Oddswire-Credits-*`, `X-Oddswire-Credit-Cost`, `X-Oddswire-Usage-State` and `X-Request-ID` describe admission/delivery state. Current account usage is authoritative; these headers are not proof the client received every byte.

## Conditional requests

For an identical query, you may send the previous `ETag` as `If-None-Match`. A 304 is only usable with the matching locally stored representation. Current access and freshness still apply; a former permission or price cannot be kept active by caching.

## Bounded pagination

When `meta.next_cursor` is nonempty, pass it unchanged as `cursor` with the same namespace and filters. Follow pages explicitly, set your own page/row limit, and stop on errors or repeated cursors. Each completed data page may cost a credit. An empty cursor ends traversal; do not fabricate one.

A 409 means the cursor no longer matches current query/authority/data semantics. Start a fresh traversal only after deciding that is appropriate. Metadata or coverage changes must not be hidden by silently continuing an old result set.

For management operations that accept a UUID `request_id`, preserve that ID and identical input when reconciling an uncertain mutation. Do not create a new billing request ID to recover from a lost response. Billing remains a restricted test contract, not public checkout.
